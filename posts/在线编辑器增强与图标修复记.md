这段时间博客陆续冒出来几个 Bug，有的靠用户反馈才发现（比如图标一片灰），有的藏在代码里直到切换页面才暴露（比如样式丢失）。这篇按时间顺序把修过的 Bug 全部记一遍，定位过程和最终解法都在，方便以后回看。

## 一、网站收藏页图标大面积变灰

### 现象

用户反馈：「好几个网站的图标显示不对，显示的是灰色的 `https://a.favicon.im/` 网站图标」。打开网站收藏页一看，确实一片灰圆圈，只能看出是个占位图。

### 定位

先检查内容仓库的 `data/website.ts`，发现每条书签都手写了 `imgurl: "https://favicon.im/域名"`。

问题就在这：`favicon.im/域名` 是 **favicon.im 的官网页面链接，不是图片接口**。真正直接返回图片的是 `https://a.favicon.im/<域名>`。也就是说，收藏页里那 50+ 条图标链接绝大部分都指向了一个 HTML 页面，浏览器渲染不出来，只好显示默认占位。

用 curl 对比验证了一下两个地址的返回内容，确认一个返回 HTML、一个返回图片，坐实了根因。

### 修复

写了个批量脚本 `scripts/regenerate-website-icons.mjs`，逐条按 `siteurl` 的根域名重算 `imgurl`，统一替换成 `a.favicon.im` 真接口，一次全量修复。

```bash
node scripts/regenerate-website-icons.mjs
```

## 二、批量脚本自己踩的正则坑：重复 imgurl

重算 `imgurl` 时，第一版脚本的逻辑是「在 `siteurl` 这一行后面插入一行新的 `imgurl`」。跑完一检查，出问题了：**每条网站都有两个 `imgurl`**。

原因很直白——`website.ts` 的对象里 `imgurl` 字段本来就在 `siteurl` 的前面，脚本盯着 `siteurl` 行往下插，旧的 `imgurl` 原封不动，新的又插了一份，同一个对象里两个 `imgurl` 打架，浏览器只认第一个（还是旧的失效链接）。

改成「只替换旧 `favicon.im` 接口的 `imgurl` 的值，不新增行」之后才干净：

```js
// 只改旧接口那行，而不是插入新行
line = line.replace(/(imgurl:\s*"https:\/\/favicon\.im\/)[^"]*(")/, "$1" + domain + "$2");
```

## 三、灰色兜底图标的检测：257 字节 SVG 的玄机

全量替换完，还有几个站图标依然是灰的。这次不是链接失效，而是 `a.favicon.im` 服务本身没拿到图标，返回了兜底图。

我写了个检测脚本，用浏览器 UA 去请求每个 `a.favicon.im/<域名>`，发现 fallback 有个很明显的特征：**返回 257 字节的 SVG**，内容固定是一个灰色圆圈加白色斜体 `f`：

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 100 100">
  <circle cx="50" cy="50" r="40" fill="#808080" />
  <text x="50" y="65" font-family="Times New Roman, serif" font-size="50" fill="white" text-anchor="middle" font-style="italic">f</text>
</svg>
```

检测一圈下来，这类灰色图标主要是三种情况：

1. **根域名抓不到，但 `www.` 子域能抓到**。比如 `agedm.io` 失效，换成 `www.agedm.io` 就返回正常 JPEG。favicon 服务抓取时可能只试了裸域；
2. **镜像/特殊站本身没有公开 favicon**。比如 Z-Library 镜像 `zh.kid1412.by`，连接直接超时，抓不到自然回退；
3. **学校/老站压根没配 favicon**。比如 `hfyz.net` 的 `/favicon.ico` 直接 404。

这三类没有统一解，得逐个处理：能用 `www.` 子域的换子域，没有 favicon 的换用站点真实可达的图标地址，实在没有的就只能保留占位。

> 顺带提醒：这类批量脚本的结果后来差点被覆盖——内容仓库远程的 `website.ts` 在 CMS 后台有过一次 378 行新增的提交，本地不先 `pull` 就跑脚本，rebase 时本地改动会被整个丢掉。跑脚本前一定要先同步。

## 四、站内切换后样式、导航栏丢失

### 现象

博客用了 Swup 做站内无刷新切换。用户反馈：**点击站内链接跳转后，页面样式和导航栏丢了，只有刷新才能恢复**。

### 定位

这是 Swup 更新 `<head>` 的经典竞态：切换页面时 Swup 要把新页面的 `<head>` 差异合并进来，但旧页面有大量内联 `<style>` 和共享 CSS，做「差量更新」时新旧 head 里没有对应上的标签会被移除。CSS 一被摘掉，整站样式瞬间崩掉，刷新（重新走一次完整文档加载）才恢复正常。

雪上加霜的是，当时构建配置是 `cssCodeSplit` 默认开启，**每页有 19 个独立 CSS 文件**，串行排队加载，切换时不仅容易丢样式，还长期转圈。

### 修复

两个配置一起改，都在 `astro.config.mjs`：

**1. Swup 的 `updateHead` 改为对象形式，仅生产环境开启：**

```js
updateHead:
    process.env.NODE_ENV === "production"
        ? { awaitAssets: true, persistAssets: true, persistTags: true }
        : false,
```

- `awaitAssets: true`：等新页面的样式表加载完成后再替换内容，避免先切内容后补样式导致的闪崩；
- `persistAssets: true`：把共享 CSS 标记为常驻资源，不反复移除/重加；
- `persistTags: true`：保留所有既有 head 标签（含内联 `<style>`），只新增缺失项，从机制上杜绝「差量竞态」把样式摘掉。

**2. 关闭 CSS 代码分割，全站样式合并为单个 CSS 文件：**

```js
build: {
    cssCodeSplit: false,
}
```

原来每页 19 个 CSS 请求串行排队是切换转圈的根源，合并后每页只请求 1 个 CSS（压缩后约 50KB），加载和站内切换都快了，而且单一共享 CSS 配合 `persistAssets` 保护更彻底。

修复后站内随便跳转，样式、导航栏都稳定，不再需要刷新。

## 五、在线编辑器推送 404：GitHub API 的 ref 与 refs

### 现象

在线编辑器（Pages CMS 后台）做「统一推送」时，GitHub API 一直报 `PATCH ... 404 Not Found (ref-update)`，但读数据一切正常。

### 定位

问题出在我图省事复用了读取时的 URL。GitHub Git Data API 这两个端点长得几乎一样，但**一个是单数 `ref`，一个是复数 `refs`**：

- 取单个引用：`GET /git/ref/heads/{branch}`（单数 `ref`）；
- **更新分支引用：`PATCH /git/refs/heads/{branch}`（复数 `refs`）**。

我用读数据的单数 `ref` 去拼 PATCH 的 URL，GET 能成、PATCH 直接 404。查了文档才反应过来是端点不一样。

### 修复

PATCH 改成复数 `/git/refs/`，一行搞定。

```bash
# 错误：GET 用的单数 ref 被复用到了 PATCH
PATCH /git/ref/heads/main          # → 404

# 正确：更新引用必须用复数 refs
PATCH /git/refs/heads/main         # → 200
```

## 六、推送失败：Update is not a fast forward

### 现象

推送时遇到 `Update is not a fast forward (ref-update)` 直接失败。

### 定位

原因是内容仓库远程已经有了新提交——CMS 后台每次编辑都会产生一次提交（尤其动到 `website.ts` 时），本地分支因此落后。本地直接 push 时服务器拒绝，因为不是快进合并。

### 修复

先 `git pull --rebase` 把远程新提交拉下来、本地提交变基到最前面，再 push，就变成 fast-forward 了：

```bash
git pull --rebase git@github.com:yujing0208/yujingblog-content.git master
git push   git@github.com:yujing0208/yujingblog-content.git master
```

> 提醒：如果远程的 `website.ts` 已经被 CMS 后台改过，本地跑批量脚本前务必先 `pull`，否则你的修改会在 rebase 时被覆盖掉——图标修复那批就白跑过一次。

## 小结

这次一共修了六个 Bug，共性都是「现象好找、根因难猜」：

- favicon 把官网链接当图片接口用，图标一片灰；
- 批量脚本在字段顺序上栽了跟头，重复插入 `imgurl`；
- 灰色兜底图靠 257 字节 SVG 特征识别，三类失效各有各的解法；
- Swup 差量更新 head 导致样式丢失，`persistTags` + 合并 CSS 双管齐下；
- GitHub API `ref`/`refs` 一字之差，PATCH 404 查半天；
- 远程有 CMS 提交时直接 push 被拒，rebase 一下就好。

写代码的人最懂：Bug 不可怕，可怕的是同一个坑踩第二次。这篇就是我的「踩坑记录」，下次再遇到直接翻这篇。
